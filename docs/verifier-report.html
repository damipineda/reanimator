Reanimator verifier report: Lunar Lander

Overall verdict: FAIL

What this verdict actually means: 2/3 scenario(s) fully measured and matching (crash-tilt, free-fall); 1 scenario(s) measured and DIVERGING (soft-landing).

Compares the real original (PhET's Lunar Lander .swf, run via a self-hosted Ruffle build, read via OCR - no JS bridge exists into it) against the hand-built HTML5 rebuild (src/rewrite/reference/lunar-lander/, read via its own exact window.__reanimator.getState() debug hook), across 3 scripted scenarios. The original was run 3x per scenario to measure its own natural run-to-run spread (its physics uses real wall-clock dt, not a fixed step); the rebuild's single run is checked against that measured spread, not against one single original run.

Scenarios

crash-tilt PASS

This tests the ANGLE-based disqualification path of the landing-classification rule, distinct from free-fall.json's speed-based disqualification (both end 'crashLanded', but for different reasons - this scenario's landing speed alone, at angle=0, would still exceed damageLandingSpeed, so this is a deliberately unambiguous positive-angle case, not a test of the asymmetric angle<0.2 quirk noted in docs/KIRO_NOTES.md (which specifically concerns NEGATIVE angles bypassing the check) - that quirk is documented but not covered by a dedicated scenario here, for time reasons.

Expected outcome: crashLanded, destroyed (angle ~0.26 rad > 0.2 disqualifies softLanded/hardLanded regardless of speed; speed is still ~12.6+ m/s from the unmodified free-fall descent, so this would have been crashLanded on speed alone too - this scenario is about confirming the angle path is also wired correctly, not about producing a different outcome label).

soft-landing FAIL

A 'suicide burn': free-fall (no thrust) for the first 3.74s, then 7 discrete Up-arrow presses fired 20ms apart (each one +2250 thrust via increaseThrust(), reaching 15750 total) to decelerate sharply before touchdown. Timeline found by src/verify/design-soft-landing.mjs (idealized fixed-40ms-tick simulation of the reference physics.js, predicting ~0.58 m/s). An earlier 9-press/5.0s candidate (idealized prediction ~0.97 m/s) measured 2.05-2.06 m/s against the REAL rebuild in a browser - over the 2 m/s threshold - because real Playwright/CDP dispatch latency between 9 rapid keydown calls delays full thrust more than the idealized simulation accounts for (a systematic effect, not the random per-tick jitter an earlier +/-40%-jitter check had tested for). This 7-press/3.74s config was chosen by testing several candidates directly against the real rebuild and was then repeated 3x for consistency: measured 1.01, 0.96, 1.08 m/s across those 3 real runs, all comfortably softLanded - see docs/KIRO_NOTES.md for the full account of finding and fixing the first (too-marginal) candidate.

Expected outcome: softLanded with a comfortable real-world margin (~1.0 m/s vs. the 2 m/s threshold, measured over 3 real runs). Angle stays 0 throughout since no Left/Right key is ever sent.

OCR limits on this scenario: VERDICT: DIVERGES (on exact landing speed, not on category). This scenario's methodology went through three corrections, each one found and fixed rather than papered over - full account in docs/KIRO_NOTES.md: (1) the original first appeared to 'never land' - this was a ~220ms settle delay in the click helper landing BEFORE t0 instead of after, enough to tip this knife-edge 'suicide burn' scenario every time; (2) fixed, it then appeared to land HARD at 2.8 m/s, diverging from the rebuild's SOFT ~1.0 m/s - but that run still had OCR running synchronously inside the real-time scripted-event loop, which was quietly delaying later keypresses by up to ~970ms; (3) with OCR fully decoupled from timing AND the click properly aligned, 3 repeated runs ALL landed SOFT (1.0, 0.7, 1.1 m/s) - matching the rebuild's own category. The STANDARD PIPELINE above now uses this same aligned click path (updated this pass) and a widened final checkpoint (21s -> 24s, timing margin only, not a physics constant) so neither side's own landing-time variance causes a spurious 'still airborne' read: both now land SOFT, and the category MATCHES. The exact magnitude still differs: original 0.5-1.0 m/s (2 of 3 runs - one had an unreadable landing message) vs. rebuild's 0.23 m/s - roughly 2-4x softer in the rebuild, outside the OCR display-rounding tolerance, hence the FAIL above despite the matching category. An aligned, OCR-decoupled altitude/thrust/fuel time series (see docs/KIRO_NOTES.md) found this gap starts specifically when thrust engages (free-fall matches within ~0.6m beforehand) even though BOTH sides apply the identical thrust value at every matched sample - ruling out input handling/key-repeat. Two candidate mechanisms remain (a small mass/thrust-constant imprecision vs. a dt-measurement difference under Ruffle's AVM1 emulation, which free-fall's small constant acceleration never exercises) but could not be told apart within this investigation's time-box. Per this round's explicit instruction, this is documented as unresolved, not forced - the recovered constants in physics.js are direct transcriptions of the decompiled source, not approximations with a 'more correct' value waiting to be found, so narrowing this gap further without a confirmed mechanism would mean guessing a number to match the original rather than citing one - exactly what this project does not do.

Measurement noise floor

Before trusting any small gap between the original and a rebuild as a real divergence, how much of a gap could pure measurement timing alone explain? Logged the real elapsed time when each OCR screenshot was actually captured vs. its SCHEDULED time (the jitter), and multiplied by the hand-built rebuild's own exact velocity at that moment (the best available velocity estimate, since OCR cannot read velocity reliably) to get an implied altitude uncertainty, for the soft-landing scenario, aligned start, OCR decoupled from the real-time loop (see src/verify/log-three-way-aligned.mjs):

An earlier version of this measurement showed jitter as high as ~970ms throughout, which would have swamped any real signal - that turned out to be a bug in the measurement itself (OCR was running synchronously inside the real-time scripted-event loop, so its own several- seconds-per-sample cost was bleeding into later samples' schedules - fixed by decoupling screenshot capture, which must stay real-time-accurate, from OCR, which does not need to). With that fixed, the noise floor is small (well under 0.3m) everywhere except briefly during the densest keypress activity, where it is still under 2m - smaller than the ~3-5m gaps this investigation measured between the original and a rebuild during the sustained thrust phase, so those gaps are reported as a real signal, not noise, in the section below.

The AI-only rebuild loads and plays with zero console errors in all 3 scenarios, and matches the hand-built reference's outcome category on 2 of 3 (free-fall, crash-tilt) - both land at the SWF's own displayed precision, 12.7 m/s. soft-landing diverges: the hand-built reference lands softly (~1.0 m/s) on the exact same scripted thrust-burst timeline; the AI-only rebuild consistently lands at 4.5-4.6 m/s (hardLanded), across 3 repeated real-browser runs - not a one-off fluke. Root cause, confirmed via two follow-up checks (not left as a guess): running both implementations' physics.js directly in Node with an idealized fixed 40ms tick (no browser) gives nearly IDENTICAL landing speeds for both (~1.83 m/s, both softLanded) - ruling out a formula bug. Logging thrust/altitude over time in both real browsers shows BOTH rebuilds register all 7 Up-arrow presses identically, reaching full thrust (15750N) at the same wall-clock time (~3.9s) - ruling out input handling. What the log DOES show: the AI-only rebuild is already falling measurably faster and further than the hand-built one BEFORE the burn even starts (and even at the test script's own "t=0" sample). Cause: the hand-built rebuild's clock starts exactly when the test script clicks its Start button (the two are synchronized by construction); the AI-only rebuild has no Start button - it auto-starts during its own async boot(), before the test script's own clock begins, giving it an unaccounted-for head start. This is a gap in the test harness's synchronization for an auto-starting app, not a bug in the Rewriter's physics or keyboard handling - see work/verify-results/soft-landing-timeseries.json and docs/KIRO_NOTES.md for the full log and reasoning. Per the task that produced this comparison, the AI-only rebuild itself was run exactly as the Rewriter produced it - not tuned, not fixed; only the TEST's own synchronization gap was found and explained, which is a separate thing from fixing the artifact.

Update: a later three-way comparison (original + hand-built + AI-only, all aligned - see src/verify/log-three-way-aligned.mjs) tried a tighter alignment for the AI-only rebuild (polling its own already-rendered vy-value text for the first post-start change, instead of page-load-settle), which reduced but did NOT fully close its head start: it still reads measurably lower altitude than the hand-built rebuild through pure free-fall (e.g. ~37m vs. ~40.5m at t=3500ms), more than the <=1-tick (~40ms) residual uncertainty that polling method should leave. Not chased down further this pass (secondary to the original-vs-hand-built investigation this round prioritized) - a known, smaller, still-open gap, not silently left unmentioned.
